## 1. e2e とは

TesterArmy が公開している、Web とモバイル向けの **オープンソース（Apache-2.0）の E2E テストフレームワーク**です。TypeScript で書きます。

特徴は、1つのテストの中で次の2種類を混ぜて書けることです。

| 書き方 | 例 | モデル呼び出し |
|---|---|---|
| 従来型（ロケータ + アサーション） | `expect(screen.getByText('...')).toBeVisible()` | 不要 |
| エージェント型（自然言語のゴール） | `agent.act('Pro プランにアップグレードする')` | 必要 |

### 仕組みのポイント

- **`agent.act`**: 自然言語で書いた操作をエージェントが実行します。
- **`agent.assert` / `waitFor` / `extract`**: 画面の内容を自然言語で判定・待機・抽出します。常にモデルを呼びます。
- **リプレイキャッシュ**
  - 後続の検証（ロケータのアサーションや `agent.assert`）が通った `act` の操作は記録されます。
  - 次回以降は **モデルを呼ばずに再生**されます。
  - 画面が変わって再生に失敗した場合は、エージェントがその時点の画面から引き継ぎます。
  - 記録は `.e2e/cache/` に JSON で保存されます。プロンプト、スクリーンショット、シークレット値は含まれません。
  - ミスする条件、CI での既定、ハンドオフの扱いは、この章末の「キャッシュの前提とハンドオフ」にまとめています。
- **モデルは自分で用意**: ChatGPT / GitHub Copilot / SuperGrok などのサブスクリプション、API キー、ローカルモデルが使えます。エージェントを使わないテストはモデル不要です。
- **エンジン**
  - Web: Playwright 経由で Chromium / Firefox / WebKit（`@e2e-dev/web`）
  - モバイル: agent-device 経由で iOS シミュレータと Android エミュレータ（`@e2e-dev/mobile`）
  - クラウド実行: Limrun、EAS Simulators、TestMu（TestMu は実機あり）
- **サンプルプロジェクト**: Vite、Next.js、Astro、Expo、SwiftUI、Jetpack Compose、Kotlin Multiplatform、Flutter、.NET MAUI
- **CI**: GitHub Actions、EAS Workflows、Bitrise、Codemagic など。`--shard`、`--last-failed`、JUnit 出力、GitHub PR コメント用リポーターがあります。

### キャッシュの前提とハンドオフ（`docs/cache.mdx` より）

「2回目以降はモデルを呼ばずに再生される」は、いくつかの前提が成り立つ場合の話です。費用は、キャッシュのヒット率に依存します。

**記録される条件**

- 既定の `read-write` モード（ローカルの既定）では、試行のあとに続く検証が通った `act` だけが記録されます。検証になるのは、ロケータのアサーションや `agent.assert` などです。確認されなかったステップは保存されません。
- 失敗した試行は、未検証の記録を削除します。
- 記録は `.e2e/cache/` に JSON で保存されます。

**ミスする条件（モデルが再び走る）**

- テスト名、`describe` グループ、ターゲット名を変えた。
- テストファイルを移動した。
- 指示文や通常のパラメータを変えた。日本語の文言を直すだけでもミスします。
- エンジン、プロジェクト ID、アプリの識別子を変えた。
- モデルを変えてもミスにはなりません。
- タイムスタンプや毎回変わるメールアドレスは `unique()` で包みます。ただし `unique()` の値が別のパラメータの値と一致または内包されると、そのステップは記録されません（`param-collision`）。

**CI での既定**

- `cache` を設定していない CI では `read-only` が既定です。CI で新しい記録は作られません。
- そのため、記録をコミットするか、`E2E_CACHE_DIR` や `--cache-dir` で共有ディレクトリを指す必要があります。
- 記録が当たらない CI では、毎回モデルが走ります。

**常にライブ実行される部分**

- `agent.assert`、`waitFor`、`extract` は常にモデルを呼びます。
- `--strict-cache` を付けても、一度も記録されていないステップ（新規または編集したステップ）はライブ実行になります。strict の実行は、記録の書き込みも削除もしません。
- `--strict-cache` で防げるのは、古い記録が失敗に変わる前にモデルへ流れることです（`REPLAY_STALE`、終了コード 2、再試行なし）。新規ステップの費用は防げません。

**ハンドオフ（再生中にエージェントが引き継ぐ）**

- 再生中に画面が記録と合わなくなると、エージェントがその時点の画面から引き継いで、最後まで進めます。
- 引き継ぎや再生失敗の理由は、`target-not-found`、`target-ambiguous`、`wrong-context`、`gap`、`action-failed`、`action-uncertain`、`viewport-changed`、`end-mismatch`、`agent-concluded` などです。
- 各ステップの `step.cache` に、`replayed`、`handed off`、`missed` のいずれかと理由が出ます。

**ハンドオフのリスクと対策**

- リスク（私の推測）: UI が壊れていても、エージェントが別の経路で目的を達成してテストが通り、回帰を見逃す可能性があります。同じ指示でも、実行ごとに経路が変わる可能性があります（非決定性）。
- 対策（私の提案）:
  - 重要フローの最終検証は、必ずロケータで決定的に書きます。
  - CI で `handed off` が出たステップは、レポートで確認してレビュー対象にします。
  - PoC で意図的に UI を壊し、テストが失敗として検出するかを確認します。

## 2. 具体例

### 例1: README のサンプル（課金アップグレード）

```ts
import { test, expect } from 'e2e';

test('a member upgrades to Pro', async ({ app, agent, screen }) => {
  await app.open('/settings/billing');

  await agent.act('upgrade the workspace to the Pro plan');
  await agent.assert('the invoice preview shows a prorated amount');

  await expect(screen.getByRole('status')).toContainText('Pro');
});
```

- 「Pro プランにする」までのタップ手順は書きません。エージェントが画面を見て実行します。
- 2回目以降は、手順が記録されていればモデルを呼ばずに再生されます。
- 最後の `expect` は、決定的なロケータ検証です。

### 例2: Maestro の YAML を e2e に置き換える（公式移行ガイドの対応表より）

Maestro:

```yaml
- launchApp:
    clearState: true
- tapOn: "Get started"
- inputText: "ada@example.test"
- assertVisible: "Check your inbox"
- scrollUntilVisible:
    element: "Resend"
- assertVisible:
    id: "resend"
```

e2e:

```ts
await app.clearState();
await agent.act('get started with the email {email}', { params: { email } });
await expect(screen.getByText('Check your inbox')).toBeVisible();
await screen.scrollUntilVisible(screen.getByTestId('resend'));
await expect(screen.getByTestId('resend')).toBeVisible();
```

`tapOn` と `inputText` の2行が、1つの `agent.act` にまとまっています。

### 例3: モバイルの設定ファイル（`docs/mobile.mdx` の記述をもとにした例）

```ts
import type { E2EConfig } from 'e2e';
import { mobile } from '@e2e-dev/mobile';

const app = { bundleId: 'com.example.app', appPath: './build/MyApp.app' };

export default {
  targets: [
    { name: 'iphone', engine: mobile({ platform: 'ios' }), app },
    { name: 'pixel', engine: mobile({ platform: 'android' }), app },
  ],
  workers: 1,
} satisfies E2EConfig;
```

### 例4: CI でシャーディングする（`docs/ci.mdx` より）

```yaml
- run: npx e2e run --shard ${{ matrix.shard }}/3 --reporter list,junit
```

## 3. Maestro との違い

| 観点 | Maestro | e2e (TesterArmy) |
|---|---|---|
| 記述形式 | YAML のフロー | TypeScript |
| 制御構文 | 限定的（`runFlow` の `when` など） | `if`、ループ、関数、フィクスチャが使える |
| 操作の指定 | 画面要素の指定が中心（`tapOn` など） | 要素指定に加え、自然言語のゴール（`agent.act`） |
| AI | `assertWithAI`、`extractTextWithAI` など一部 | `act`、`assert`、`waitFor`、`extract` が中核 |
| 再実行のコスト | 毎回同じ手順を実行 | 成功した `act` は記録を再生（モデル呼び出しなし） |
| 対象 | モバイル中心（Web も可） | Web（Playwright）とモバイル（agent-device）を同じ書き方で扱う |
| 実行環境 | ローカルと Maestro Cloud | ローカル、自前 CI、ホスト型デバイス（Limrun、EAS、TestMu） |
| 成熟度 | 広く使われている | 1.0 前で、API が変わる可能性がある |
| モデルの準備 | 不要 | エージェント手順には必須（サブスクリプション、API キー、ローカルモデル） |
| 成果物 | JUnit など | 各呼び出しがレポートのステップになる。トレース、スクリーンショット、手順ごとの動画（`--video`）もある |

### 移行時に注意が必要な点（公式移行ガイドより）

- **セレクタの一致規則が変わります。** Maestro は text/id を大文字小文字無視の正規表現として扱います。e2e は完全一致で、大文字小文字も区別します。
- **複数ヒットするとエラーになります。** Maestro は最初の一致をタップします。e2e は `LOCATOR_AMBIGUOUS` で失敗するので、必要なら `.first()` を付けます。
- **空間セレクタがありません。** `below`、`above`、`leftOf`、`rightOf` は未対応です。ラベル、testID、エージェントのゴールで代替します。
- **未対応の機能があります。** `addMedia`、`assertDarkMode`、HTML レポート、`copyTextFrom`、`pasteText`、Maestro Studio などです。`npx e2e mcp` が Studio に近い代替とされています。
- **併用できます。** 両方のランナーが同じシミュレータやエミュレータを共有できるので、1フローずつ移行できます。
- **シークレットの扱い。** 認証情報はモデルに見せない設計です。`credentials` と `secrets` で渡します。

## 4. あなたの業務への活用案

「業務で Maestro を使っている」という情報だけで、アプリの種類や運用体制は分かっていません。以下は一般的な使いどころからの提案です。実際のフローに合わせて取捨選択してください。

### 活用案A: 壊れやすいフローをエージェントに任せる

- 例: オンボーディング、ログイン、課金、アンケート、A/B テストで文言や並びが変わる画面。
- Maestro では文言やレイアウトの変更でセレクタが壊れやすい部分です。
- `agent.act('メールアドレス {email} で登録を始める', { params: { email } })` のように書きます。
- 最後の検証だけは `expect(...)` で決定的に書きます。
- 手順が記録されて当たり続ける間は、モデルのコストがほとんどかかりません。指示文やテスト名を変えると再びモデルが走ります（第1章「キャッシュの前提とハンドオフ」）。

### 活用案B: Web と iOS/Android の同じシナリオを1つの書き方で

- ログインから購入完了までのように、画面は違っても意図が同じシナリオに向きます。
- `targets` に iOS と Android を並べれば、同じテストを両方で走らせられます。

### 活用案C: 回帰の「想定外」を探す

- ドキュメントに `explore.mdx`、`bug-bash.mdx`、`visual-testing.mdx` があります。
- 固定シナリオ以外の探索的テストや、見た目の確認にも使えるようです。
- 内容は未確認なので、PoC で試す価値があります。

### 向かないケース（当面は Maestro のまま）

- 空間セレクタに強く依存しているフロー。
- Maestro の未対応機能（`addMedia`、ダークモードのアサート、HTML レポートなど）を使うフロー。
- モデルへの画面送信に制約がある案件。指示文やアクセシビリティツリーなどがモデルへ送られます（9.2 の「モデルに送られるもの／送られないもの」の表）。画面上の個人情報も含まれうるため、機密性の確認が必要です。ローカルモデルを使う選択肢はあります。
- 安定性が最優先で、API 変更への追従コストをかけられない場合。

### 推奨する進め方（PoC）

1. **まずモデルなしで動かす。** `npx e2e init` のサンプルはモデル呼び出しなしで動きます。環境（Node 24.8+、Xcode / Android SDK）と `npx agent-device doctor` を確認します。
2. **既存の Maestro フロー1本を移行する。** `docs/migrate/maestro.mdx` の対応表に沿って変換します。
   - 最初は、ロケータだけで書く版と、`agent.act` を使う版の2つを作って比べます。
   - Maestro と同じシミュレータで並走できます。
3. **測るもの**: 初回と2回目以降の所要時間、トークン消費（実行サマリに出ます）、キャッシュのヒット率、画面変更時の復旧（引き継ぎ）の成功率。あわせて、意図的に UI を壊したときにテストが失敗するか（ハンドオフによる誤パスがないか）を確認します。
4. **CI へ**: `--strict-cache` と `--last-failed`、JUnit 出力を試します。iOS は macOS、Android は KVM 付きの Linux で、ジョブを分けます。
5. **判断基準**: Maestro のメンテナンス工数が減るか、モデル費用とのトレードオフが見合うか。

## 6. 追加調査: Test Filters API（2026-10-23 時点）

X の投稿で話題になっていた Test Filters API について、リリースノートと PR で確認しました。実際に動かしての検証はしていません。

### 概要

PR が影響しうるテストだけを実行する機能です。毎回全テストを回すと遅くて高くつく、という動機で追加されました（[PR #1206](https://github.com/tester-army/e2e/pull/1206)）。

| 項目 | 内容 |
|---|---|
| フィルタの仕組み | `@e2e-dev/github` 0.4.3 が `filters` を提供 |
| AI による判定 | `@e2e-dev/decision` 0.3.0 の `decisionFilter({ model })`。リリースノートの例は `gateway.decisionModel('typesafe-ai/jev')` |
| カスタムフィルタ | 自分で書ける。設定ファイルは `context.configFile` として読める |
| 必要なバージョン | e2e 0.21.3 以上 |
| 実行方法 | `npx e2e run --changed-since origin/main` |
| 事前確認 | `npx e2e list --changed-since origin/main` で除外結果をプレビュー |

設定のイメージ（リリースノートの記述から組み立てたスケッチで、未実行）:

```ts
import { decisionFilter } from '@e2e-dev/decision';

export default {
  // ...
  filters: [decisionFilter({ model })],
} satisfies E2EConfig;
```

### 判定の安全設計（PR #1206 の説明より）

- decision model が、差分でテストの検証内容が変わる確率と、保存したセッション設定が壊れる確率を見積もります。両方が20%未満のときだけ除外します。
- 次の場合は全テストを実行します。
  - 設定ファイルやロックファイルの変更
  - テストファイル、セットアップファイル、スナップショットの変更
  - `--last-failed` での再実行
  - `pull_request_target` での実行（フォークの差分がシークレットと同じ場所でモデルに渡るのを避けるため）
- 比較対象がない実行（main への push、マージキュー、ローカル）は全テストを実行します。
- 除外されたテストは PR コメント、`junit.xml`、レポートに残ります。実行対象がゼロならエンジンもアプリも起動しません。

### decision model と Jev

- decision model は、自由な文章を生成せず、選択肢に確率を付けて答えるモデルです（[`docs/decision-models.mdx`](https://github.com/tester-army/e2e/blob/main/docs/decision-models.mdx)）。
- フィルタ以外に、`agent.act` と `agent.assert` を LLM エージェントの代わりに decision model で動かす使い方もあります。
- Jev は TypeSafe AI のモデルです（`@ai-sdk/typesafe-ai`、`TYPESAFE_AI_API_KEY`）。docs にモデル自体の説明はなく、OpenAI の `gpt-6-luna` なども使えるとされています。

### 導入判断の観点

- 数本の PoC では恩恵が小さく、テストが数十本に増えて CI の時間や費用が気になってから検討すれば十分です。
- フィルタ自体がモデルを呼ぶため、その費用も含めて損得を測る必要があります。リリースノートに料金や呼び出し回数の記載はありません。
- `decisionFilter` は PR の差分（ソースコード）をモデルに送ります。ソースコードの外部送信が社内ルール上問題ないか確認が必要です。`providerOptions` でゼロデータ保持などを設定できるとされています。
- 判定が外れて必要なテストが落ちるリスクがあるため、main への push では全件実行する運用が保険になります。

### バージョンの動き

初回調査時の最新は 0.18.0 でしたが、2026-10-23 時点では e2e 0.21.3 です。更新が活発で、API が変わる前提で、PoC ではバージョンを固定してください。同じリリースで `e2e upgrade`、`e2e init --example`、JavaScript の設定ファイル対応、`--action-timeout` / `--assertion-timeout`、Playwright 1.64.1 への更新も入っています。

## 7. 追加調査: 紹介動画（ライブ配信）の要約

TesterArmy の開発者アドボケイトによる、e2e の紹介ライブ配信の文字起こしを要約したものです。話者の発言をまとめたもので、私たちの環境での検証結果ではありません。

### 2つのプロジェクト

- TesterArmy には、エージェント型テストの SaaS（TesterArmy プラットフォーム）と、無料のオープンソースフレームワーク（e2e）の2つがあります。
- 現時点では別プロジェクトで、将来統合する可能性があるそうです。
- 公開から3週間で、GitHub のスター約1.1万、npm ダウンロード60万超とのことです。

### 開発の動機

- test ID、CSS クラス、iframe 名のような実装の詳細に依存するテストは、デザイン変更やサードパーティ側の変更で壊れます。
- コーディングエージェントにテストを書かせると、コードを見て実装に沿ったテスト（ホワイトボックス）になり、脆くなりがちです。
- e2e は、ユーザーが実際にやる操作（ユーザーフロー）をテストする考え方です。

### 仕組み

- `agent.act` は操作を平易な言葉で指示し、`agent.assert` は状態の変化をエージェントが判定します。Playwright や Maestro と同じ決定的な API（`getByRole`、`getByText`、`getByTestId`）とも混在できます。
- 1回目はエージェントが実行し、`act` の操作が記録されます。2回目以降は、記録が当たる限りほぼ無料で再生される、と説明しています（ミスする条件は第1章）。`agent.assert` は毎回エージェントが判定するため、キャッシュされません。
- アプリが変わって再生に失敗すると、その時点からエージェントが引き継ぎます。
- 画面とアクセシビリティツリーしか見ないブラックボックス型なので、フレームワークの種類やアーキテクチャに依存しません。

### 探索エージェントとバグバッシュ

- コードを書かずにアプリを壊しにいく探索エージェントを、PR ごとに走らせられます。結果はレポートになり、コーディングエージェントに渡して一括で直せます。
- 探索エージェントを6〜7個同時に走らせるのが「バグバッシュモード」で、PR ごとに動かしているそうです。
- 検証用スキル（create verification skill）で、PR の変更前後のスクリーンショットや録画を付けて出荷できます。Web とアプリの両方に対応するとのことです。

### 対応環境

- **プラットフォーム:** Web、iOS、Android に単一の API で対応しています。土台は Playwright と agent-device で、将来変わる可能性があります。`defineEngine` で独自エンジンを足せます（Electron を実装した例があるそうです）。
- **CI:** Node.js が動けばどこでも動きます。
- **モデル:** Vercel AI Gateway 経由でほぼ何でも使えます。OpenAI、Anthropic、Qwen などの直接利用も可能です。act と assert で別のモデルを指定できます。
- **サブスク:** OpenAI、GitHub Copilot、OpenCode、SpaceX AI が使えます。Claude はサブスクを直接使えず、別途 API キーが必要です。
- **移行スキル:** Playwright、Maestro、Detox から1スイートずつ段階的に移行するスキルがあります。

### デモで分かったこと（Expo アプリ、Next.js の Venmo クローン）

- `npx e2e init` で、エンジン、モデルの渡し方、スキルと MCP の追加を選びます。`e2e.config.ts` とサンプルテストが生成されます。
- サンプルは Settings アプリを開く設定なので、自分のアプリの `bundleId` に直す必要があります。
- `workers` を増やすと、iOS、Android、Web を並列実行できます。1だと順番に実行されて遅くなります。
- ヘッドレスがデフォルトです。画面を見たいときは headed で実行します。
- 2回目の実行はキャッシュから再生され、コストが約4分の1になりました。キャッシュ率は62%でした。
- 本番に近い例では、大半がキャッシュで動き、数回は引き継ぎが発生しました。1件はキャッシュが効かず、全体をエージェントでやり直しました。
- モバイルはアニメーションなどで Web より遅いそうです。
- 認証情報は設定ファイルの `credentials` に置き、環境変数から渡せます。

### コストと運用

- **コスト:** 15テスト・6ファイルのスイートで、実行は1セント未満と話しています。大きめのスイートでも1セント未満とのことです。これは話者の発言で、モデルやアプリによって変わります。
- **モデルの選び方:** 安価なモデルで十分という感触だそうです。担当者が言及したモデル名は文字起こしでは「GPT-4o mini」ですが、公式ドキュメントの例とは名前が違うため、聞き取りの誤りかもしれません。
- **decision model:** CTO が試していて、さらに安い解決策もあるそうです。話者は自分では試していないと断っています。
- **ドル金額の表示:** API キー（Gateway 経由）なら出ます。サブスク利用では出ません。
- **キャッシュの共有:** 現状は**コミットするのが一番簡単**で、ビジュアルリグレッションのスクリーンショットのようにテスト資産として扱うよう勧めています。GitHub Actions のキャッシュや S3 も選べます。

### GitHub Actions と PR コメント

- ドキュメントの GitHub Actions のページに、エージェント用プロンプトがあります。Claude などに貼ると YAML (`e2e.yaml`) を設定してくれます。手動でコピーも可能です。
- AI Gateway のキーは、リポジトリの Secrets に登録します。
- 専用パッケージを足すと、Web、Android、iOS のテスト結果が PR にコメントされます。

### Q&A のポイント

- Playwright の generator / planner / healer のような別機能は不要で、フレームワークに組み込みの考え方です。
- Page Object Model のような特別な設計は不要です。
- Windows ソフトのプラグインに使えるかは、カスタムエンジンで可能性はあるが、話者は未検証です。

### これまでの調査との関係

- Claude サブスクを直接使えない点は、公式の `docs/subscriptions.mdx` の記述と一致しています。
- キャッシュのコミットは動画でも推奨されています。ただしキャッシュには署名がなく、レビュー対象にすべきです（`docs/security.mdx` より）。
- 動画では、サンドボックスがないこと、接続先の制限がないこと、decisionFilter が PR の差分を外部モデルに送ることには触れていません。セキュリティ面は公式の security ドキュメントで判断してください。

## 8. Web 新規導入編

前提: React Native アプリは Maestro で運用が回っているため、そのまま継続します。まだ E2E テストを導入していない別の Web プロダクトにだけ、e2e の導入を検討します。

### 向いている理由

- **移行コストがゼロです。** 第3章で挙げた Maestro との非互換（セレクタの完全一致、空間セレクタ、未対応機能）に当たりません。
- **Web エンジンは Playwright が土台です。** 1.0 前のフレームワークでも、ブラウザ操作の部分は実績のあるものに乗っています。モバイル側（agent-device）よりリスクが低いはずですが、動かして確認したわけではありません。
- **モデルなしで始められます。** ロケータと `expect` だけで書けば、モデルの契約も費用も要りません。`agent.act` は後から、壊れやすい画面にだけ足せます。

### 判断ポイント: 素の Playwright で足りるか

- **e2e が向く場合:** コーディングエージェントにテストを書かせて回したい。UI の文言やレイアウトが頻繁に変わる。非エンジニアがゴールを日本語で書けると嬉しい。
- **素の Playwright で足りる場合:** 画面が安定していて、テストはエンジニアが書く。1.0 前の API 変更に付き合いたくない。
- 初期導入のコストが小さいので、まず e2e で始めて、合わなければ Playwright に寄せる進め方でも良いと思います。ただし e2e から Playwright へ戻す公式の手順は確認できていません（確認できたのは Playwright から e2e への移行ガイドだけです）。

### 具体例: 最初の3本（架空の SaaS を想定）

| # | シナリオ | 書き方 | 理由 |
|---|---|---|---|
| 1 | トップが開き、ログイン画面が表示される | ロケータのみ | スモーク。モデル不要 |
| 2 | 新規登録 → メール認証 → プロジェクト作成 | `agent.act` + ロケータで検証 | 画面遷移が多く、UI が変わりやすい |
| 3 | 課金プランの変更 | `agent.act` + 最後はロケータで検証 | 重要フロー。結果は決定的に検証したい |

2本目のイメージです。API は公式ドキュメントの記述から組み立てたスケッチで、実行して確認したものではありません。

```ts
import { test } from '@e2e-dev/web';
import { expect } from 'e2e';

test('新規登録してプロジェクトを作る', async ({ app, agent, browser }) => {
  await app.open('/signup');

  await agent.act('メールアドレス {email} で登録し、プロジェクト「{name}」を作成する', {
    params: { email, name },   // email は unique() で毎回別の値にする
  });

  await expect(browser.getByRole('heading', { name: name })).toBeVisible();
});
```

- 手順はエージェントに任せ、最後の成否は必ずロケータで決定的に検証します。
- 成功した手順がキャッシュに記録され、記録が当たる間はモデルを呼ばずに再生されます。テスト名やファイルの場所、指示文を変えると、再びモデルが走ります（第1章「キャッシュの前提とハンドオフ」）。
- 登録メールアドレスのような毎回変わる値は `unique()` で包みます。包まないとキャッシュが毎回外れます。ただし `unique()` の値が別のパラメータの値と一致または内包されると、そのステップは記録されません（`docs/cache.mdx` より）。

### 導入手順の提案

1. **ローカルで `npx e2e init`（Web）。** Node 24.8 以上（または 22.22.3 以上）が必要です。サンプルがモデルなしで通ることを確認します。
2. **スモークと主要フローを3本書く。** 最初は `agent.act` なしの版を作り、次にエージェント版を作って比べます。
3. **GitHub Actions に載せる。**
   - CI ではキャッシュが read-only になります。キャッシュをコミットするか、共有ディレクトリを使わないと、毎回モデルが走ります。
   - `--strict-cache` を付けると、記録が古いときにモデルを呼ばずに失敗します。ただし、新規や編集したステップ、`agent.assert`、`waitFor`、`extract` はストリクトでもライブ実行になるため、費用の上限にはなりません。上限は API キー側の月額制限などで別に設けます。
   - API キーは Secrets に入れます。フォークからの PR には渡しません。
   - 失敗時の `.e2e/`（トレース、スクリーンショット）をアーティファクトとして保存します。
4. **バージョンを固定する（私の提案）。** 1.0 前でマイナーバージョン間で設定が変わりうるため、依存はピン留めします。
5. **判断基準を決めておく。** フレークの率、初回と2回目以降の実行時間、1回あたりのモデル費用、画面変更時にエージェントの引き継ぎで復旧できた割合。意図的に UI を壊したときにテストが失敗するか（ハンドオフによる誤パスがないか）も確認します。

### 事前に確認したいこと

- **認証方法。** メールリンクや SSO、2FA があると難度が上がります。`docs/authentication.mdx` で方針を決めます。
- **テスト環境。** ステージング環境とテストデータを用意できるか。本番相手は避けたいです。
- **モデルへの送信可否。** 画面のアクセシビリティツリーなどがモデルに送られます（9.2 の表）。個人情報や機密を含む画面は、社内ルール上問題ないか確認が必要です。

## 9. セキュリティ・コスト編

### 9.1 コスト: サブスクで使えるか

[`docs/subscriptions.mdx`](https://github.com/tester-army/e2e/blob/main/docs/subscriptions.mdx) の記述です。**Claude Code のサブスク（Pro など）を e2e にそのまま使うことは、公式ドキュメント上できません。** 紹介動画でも「Claude はサブスクを直接使えず、API キーが必要」と話されています。

| プラン | e2e での扱い |
|---|---|
| ChatGPT Plus/Pro、GitHub Copilot、OpenCode Console、SuperGrok / X Premium+ | `npx e2e login` でサブスクのまま利用可能 |
| Claude Max / Team | サインインはなく、API キーを発行して `ANTHROPIC_API_KEY` に設定する。費用は「プランの毎月の API クレジットから支払われ、プランの利用上限は消費しない」 |
| Claude のその他のプラン | API クレジットがなく、別の API プロバイダが必要 |

- 「Max / Team に毎月の API クレジットが付く」という記述は e2e 側のドキュメントの話です。Anthropic 側の仕様は未確認なので、契約中のプランと Claude Console の請求画面で確認してください。付いていても、クレジットは月末に失効するとあります。
- Pro プランなら、Anthropic の API を従量課金で別契約するか、他社モデルやローカルモデルを使うことになります。
- ドキュメントには、料金の具体的な数字も、サブスクの利用規約やレート制限の説明もありません。
- CI は公式が「API キーを使う」ことを推奨しています。ChatGPT、Copilot、SuperGrok のサブスクは CI では使えず、API プロバイダが必要です。
- Anthropic の API を使う場合は `@ai-sdk/anthropic` を使います。`docs/models.mdx` には Claude の設定例がありません。
- ドル金額の表示は API キー（Gateway 経由）の場合のみで、サブスク利用では出ません（動画での発言）。

**費用を抑えられる仕組み:**

- モデルを使うのは `agent.act` などのエージェント手順だけです。ロケータと `expect` だけのテストは、モデルも API キーも要りません。
- 成功した `act` は記録され、記録が当たる間はモデルを呼ばずに再生されます。ミスする条件と CI での既定は第1章を参照してください。費用はヒット率に依存します。
- `--strict-cache` を付けると、記録が古いときにモデルを呼ばずに失敗します。ただし、新規や編集したステップはライブ実行になるため、費用の上限にはなりません。
- `agent.assert`、`waitFor`、`extract` は毎回モデルを呼びます。
- 実行サマリにトークン数とモデル呼び出し回数が出るので、PoC で実測できます。
- 動画では、15テスト規模のスイートで1回の実行が1セント未満と発言されています。話者の発言であり、モデルやアプリによって変わります。

**PoC での進め方:** 最初は API キー不要のロケータのみのテストで始めます。エージェント手順は後から少数だけ足し、Anthropic Console に月額の上限を設定してから回すのが安全です。

### 9.2 セキュリティ

[`docs/security.mdx`](https://github.com/tester-army/e2e/blob/main/docs/security.mdx) は、制限事項も含めて率直に書かれています。

**良い点**

- アプリが表示した内容は信頼せず、モデルに道具や認証情報を与えさせない設計です。
- モデルはツール経由でしか動けず、実行前に呼び出しがスキーマ検証されます。モデルの出力が直接コードとして評価されることはありません。
- シークレットはモデルに名前だけ見せ、値はランナーが入力します。レポートやログでは `<secret:name>` に置き換わります。
- 送信内容は下の表のとおりで、スクリーンショットは必要なときだけです。
- テレメトリは匿名の利用統計で、テスト名、URL、画面の内容、認証情報は送られません。止めることもできます（`docs/telemetry.mdx`）。

**モデルに送られるもの／送られないもの**

`security.mdx`、`agent-steps.mdx`、`telemetry.mdx`、`decision-models.mdx` の記述をまとめたものです。第4章、第8章、9.3 はこの表を参照します。

| 区分 | 内容 |
|---|---|
| モデルに送られる | 指示文とパラメータ、画面のアクセシビリティツリー（テキストスナップショット。URL はマスク済み）、これまでの手順の記録。`act` にはこれまでの手順が渡り、`assert`、`waitFor`、`extract` には渡らない |
| 条件付きで送られる | マスク済みスクリーンショット。モデルが要求したとき、または step に `vision` を指定したときだけ |
| 送られうる（私の推測） | 画面に表示されている内容はツリーにそのまま入るため、表示名やメールアドレスなど、画面上の個人情報も送られうる。ドキュメントには明示がない |
| 送られない | シークレットの値（モデルには名前と用途だけが見える）。パスワード欄の値は、decision model のテキストモデルにも渡らない |
| テレメトリ（既定で有効、送信先 `eu.i.posthog.com`） | 送る: コマンド名、エンジン、モデルプロバイダとトークン合計、エラーコード、OS・CPU などの環境、リポジトリのルートコミットのハッシュ、使ったフラグの名前。送らない: テスト名、パス、URL、指示文、画面の内容、スクリーンショット、エラーメッセージ、環境変数の値、認証情報 |
| その他の通信先 | モデルプロバイダ、テスト対象のアプリ、npm レジストリ（更新確認、1日1回まで）、連携サービス（Kernel、Limrun、EAS Simulators、smol など） |
| `decisionFilter` 使用時 | PR の差分（ソースコード）がモデルに送られる（第6章） |

**導入前に必ずつぶす項目（優先度順）**

公式が明記している制限を、優先度順に並べ直したものです。対策のうち（私の提案）が付いたものは、ドキュメントに書かれていません。

| 優先度 | 制限 | 内容 | 対策 |
|---|---|---|---|
| 高 | 接続先の制限（origin allowlist）がない | アプリが別サイトへ誘導すると、エージェントはそちらへ移動し、そのステップのシークレットを使えてしまう。外部リンク、決済、SSO のリダイレクトがある Web では特に重大 | 外部へ遷移するフローは対象から外すか、テスト専用アカウントと使い捨てのシークレットだけを使う。テスト実行環境の通信先をプロキシやファイアウォールで制限する（私の提案） |
| 高 | サンドボックスがない | テスト、設定、アプリのコマンドは、実行ユーザーの OS 権限で動く | 使い捨ての隔離環境（コンテナ、CI ランナー）で実行し、本番の認証情報や社内ネットワークに触れさせない（私の提案） |
| 高 | フォーク PR | 信頼できない PR のコードをシークレット付きで実行すると危険 | 信頼できない PR のコードは、シークレットも書き込みトークンもない外部サンドボックスで実行する。モデルのキーは信頼できるビルドにだけ渡す（公式の推奨） |
| 高 | キャッシュに署名がない | 入力値はシークレットを除いてそのまま保存される。コミットしたキャッシュは、改ざんされると実行ユーザーの権限で再生される | テストコードと同様にレビュー対象にする。CODEOWNERS を設定する（私の提案） |
| 中 | 認証情報の渡し方 | `basicAuth` は任意のオリジンからの 401 に応答する。`headers` は `vercel.app` のような共有ドメイン配下の全ホストに届く。シークレットを素の文字列で渡す場合や、サインインが Cookie を設定する場合は、スクリーンショットが無効にならない | `Secret` 機能で渡す。テスト専用のドメインと使い捨てのアカウントを使う |
| 中 | マスクの範囲が限られる | 動画は何もマスクしない。スクリーンショットは secure フィールドだけマスクする。`command.log` はアプリの出力がそのまま残る。変換した値（キーの末尾4文字、base64 など）はそのまま通る | 動画を有効にする場合は、保存先と共有範囲を制限する。アーティファクトの公開範囲に注意する（私の提案） |
| 中 | テレメトリが既定で有効 | 上の表のとおり匿名の統計を送る | `e2e telemetry disable`、`E2E_TELEMETRY_DISABLED=1`、`DO_NOT_TRACK=1` のいずれかで止める。CI では環境変数だけが効く |
| 中 | `decisionFilter` を使う場合 | PR の差分がモデルに送られる | 使う前に社内で別途承認を取る。`providerOptions` でゼロデータ保持などを設定できるとされている |

### 9.3 推奨する安全対策

9.2 の「導入前に必ずつぶす項目」を、PoC 用のチェックリストにしたものです。公式ドキュメントの内容に、私の一般的な判断を加えています。ドキュメントに書かれていない項目には（私の提案）と付けています。

1. **実行環境を分離する（私の提案）。** PoC は Docker か devcontainer、または CI の使い捨て環境で行い、本番の認証情報や社内 VPN には触れさせません。
2. **対象はステージング環境とテスト専用アカウントだけにする（私の提案）。** 本番データや個人情報を含む画面には使いません。
3. **テレメトリを止める。** ローカルは `e2e telemetry disable`、CI は `E2E_TELEMETRY_DISABLED=1` を設定します。
4. **API キーは専用に発行して低い上限をかける（私の提案）。** 信頼できるブランチの CI にだけ渡し、フォーク PR には渡しません。
5. **シークレットは `Secret` 機能で渡す。** 素の文字列で渡しません。動画は保存先と共有範囲に注意します。
6. **キャッシュのコミットはレビュー対象にする（私の提案）。** CODEOWNERS を設定します。
7. **依存を固定する（私の提案）。** バージョンをピン留めし、ロックファイルをコミットして、CI は `npm ci` で入れます。新しい npm パッケージなので、導入時にメンテナと権限の変更履歴を確認します。
8. **モデルへ送るデータを確認する。** 9.2 の表のとおり、画面のアクセシビリティツリーなどがモデルに送られます。Anthropic の API を使う場合のデータ保持の条件は、契約内容を社内で確認してください。ローカルモデル（Ollama など）なら外部に出ませんが、モデルの性能次第でステップ数が増えます。

### 9.4 まとめ

- **コスト:** 最初は API 不要のテストで始められるため、実質ゼロから試せます。エージェント手順を足す段階で、API の従量課金（または Max/Team のクレジット）を決めます。
- **セキュリティ:** 設計は慎重ですが、サンドボックスなし、接続先制限なし、1.0 前という性質があります。隔離環境と使い捨てのキーで試すのが前提です。
